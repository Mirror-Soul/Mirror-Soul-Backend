# 직업 인증 수동 심사 흐름 (초안)

## 목적과 범위

- 사용자는 선택한 직업을 증명할 수 있는 사진을 제출한다. 재직증명서로 서류 종류를 제한하지 않는다.
- 관리자가 사진을 직접 보고 신청 직업을 증명하는지 판단해 승인 또는 거부한다. OCR과 자동 판정은 사용하지 않는다.
- PASS 연동은 이후 단계다. `users.name`은 온보딩 닉네임이므로 심사 이름으로 사용하지 않는다.
- PASS 도입 전에는 이름을 입력받지 않는다. 사진 속 이름과 신청자 본인의 일치 여부는 이 단계에서 판정하지 않는다.

## 사용자 제출

1. 사용자가 인증받으려는 직업을 선택하고 증빙 사진을 업로드한다.
2. 사진 원본은 비공개 S3에 저장한다. 업로드 완료 후 백엔드가 사용자 ID, 신청 직업, S3 사진 키를 연결한 인증 요청을 `PENDING`으로 접수한다.
3. S3에 파일을 올린 것만으로는 인증 요청이나 인증 완료가 되지 않는다. 백엔드가 파일 존재와 해당 사용자 소유 여부를 확인한 뒤 접수한다.

## 관리자 웹의 인증 요청 탭

- `PENDING` 요청만 목록에 표시한다.
- PASS 도입 전에는 사용자 UUID와 요청 ID로 신청을 구분하고, 그 아래에 제출 사진을 보여준다. PASS 도입 후에는 확인된 실명을 함께 표시할 수 있다. 이 묶음은 화면 표현이며 S3나 관리자 웹에 사진을 복제하는 디렉터리가 아니다.
- 사진은 관리자에게만 제한된 방식으로 S3에서 불러온다. 관리자가 요청을 열 때 발급한 짧은 유효기간의 조회 URL을 사용할 수 있다.
- 관리자 화면에는 사용자 UUID, 요청 ID, 선택한 직업, 제출 사진, 요청 시각을 함께 표시한다.

## 관리자의 판정 기준

관리자는 다음을 직접 확인한다.

1. 판정에 필요한 내용이 선명하며 가려진 부분이 없다.
2. 사진의 내용이 사용자가 신청한 직업을 증명한다고 판단할 수 있다.

두 조건을 모두 만족하면 **서류 승인**을 선택한다. 하나라도 만족하지 않거나 판단할 수 없으면 **거부**를 선택하고, 사용자가 다시 제출할 수 있도록 사유를 남긴다. 사진 속 이름이 계정 소유자와 일치하는지는 PASS 도입 후 확인한다. 서류의 진위와 현재 재직 상태는 관리자가 사진으로 확인 가능한 범위에서 판단한다.

## 판정 후 처리

| 관리자 선택 | 서류 심사 상태 | 사용자 안내 |
| --- | --- | --- |
| 서류 승인 | `APPROVED` | 서류 심사 완료, PASS 본인확인 대기 안내 |
| 거부 | `REJECTED` | 거부 사유와 재제출 안내 |

- 각 요청의 처리자, 처리 시각, 판정 결과, 거부 사유를 기록한다.
- 사용자가 다시 제출하면 새 요청을 생성하고 이전 요청의 결과도 이력으로 남긴다.
- 사진 제출 여부만으로 인증 완료를 표시하거나 인증 혜택을 주지 않는다.
- 서류 심사 상태와 본인확인 상태를 별도로 저장한다. 관리자 승인만으로는 최종 직업 인증 배지·혜택을 제공하지 않는다.
- 최종 직업 인증은 서류 심사 `APPROVED`와 PASS 실명 확인이 모두 완료된 경우에만 적용한다.

## PASS 도입 시 연결

- PASS로 확인한 실명을 승인된 서류 사진 속 이름과 대조한다. 이름을 기계적으로 읽지 않으므로 관리자 재확인 절차가 필요하다.
- 이름이 일치하면 본인확인 상태를 완료로 기록하고 최종 직업 인증을 적용한다. 불일치하면 최종 인증을 막고 재심사 절차로 보낸다.
- PASS 추가가 이전의 서류 심사 이력과 관리자 판정 결과를 덮어쓰지 않도록 두 상태를 분리한다.

## DB 구조 (V42, V44)

- `job_verification_requests`에는 신청자, 신청 직업, 서류 심사 상태, 거부 사유, 처리자와 처리 시각을 요청별로 저장한다.
- V44는 V42의 미확인 제출 이름 컬럼을 제거한다. V42가 이미 적용된 DB에서도 후속 마이그레이션으로 이름 입력을 없앨 수 있다.
- `job_verification_request_files`에는 각 요청에 속한 S3 사진의 버킷·키·표시 순서와 선택적인 S3 버전 ID를 저장한다. 한 요청에 사진을 여러 장 연결할 수 있다.
- `APPROVED`는 **서류 심사 승인**을 뜻한다. 최종 직업 인증 여부는 추후 PASS 본인확인 정보와 함께 판단한다.
- 기존 `users.job_certification_object_key`에는 심사 결과가 없으므로 예전 값을 새 요청이나 승인 기록으로 자동 전환하지 않는다.

## 사용자 제출 API

1. 기존 `POST /files/presigned-url`에 `directory: "job-certifications"`와 JPEG/PNG/WebP Content-Type을 보내 업로드 URL과 `objectKey`를 받는다.
2. 반환된 URL로 S3에 사진을 직접 PUT 업로드한다.
3. 업로드 성공 후 로그인한 사용자가 `POST /job-verifications`를 호출한다. 요청 본문은 `{"objectKeys":["job-certifications/..."]}`이며 사진은 1~5장이다. 신청 직업은 서버가 현재 사용자 프로필에서 읽어 신청 시점의 값으로 저장한다.
4. 서버는 사용자 소유 경로, S3 파일 존재, Content-Type, 실제 이미지 서명, 파일 크기(각 5 MiB 이하)를 확인한 뒤 `PENDING` 요청과 사진 기록을 저장한다.
5. 같은 사진·직업으로 접수가 재시도되면 기존 대기 요청 ID를 반환한다. 다른 신청이 이미 대기 중이면 충돌 응답을 반환한다.

업로드 URL 발급이나 S3 PUT만으로는 심사 요청이 생기지 않는다. 앱은 제출 완료 API의 성공 응답을 받은 뒤에만 '심사 중'으로 표시해야 한다. 이전 `/onboarding/profile`의 `jobCertificationObjectKey`는 기존 호환성을 위해 남아 있지만, 새 심사 요청 생성에는 사용하지 않는다.

## 심사 및 상태 조회 API

- `GET /admin/job-verifications?page=0&size=20`: 오래된 `PENDING` 요청부터 페이지로 조회한다. 각 항목에 요청 ID, 사용자 UUID, 신청 직업과 제출 시각이 있다.
- `GET /admin/job-verifications/{requestId}`: 요청 상세와 사진별 5분짜리 S3 조회 URL을 반환한다. 각 사진의 `signedHeaders`를 URL 요청에 포함해야 한다. 브라우저가 자동으로 보내는 `Host`는 응답에서 제외한다. 버전 ID가 있는 사진은 해당 버전을, 버전 ID가 없는 사진은 제출 당시 ETag와 일치하는 객체만 읽을 수 있다. 후자의 경우 브라우저에서 S3 GET 시 `If-Match` 헤더를 허용하도록 버킷 CORS 설정이 필요하다.
- `POST /admin/job-verifications/{requestId}/approve`: 서류 심사 완료로 저장한다. PASS 전에는 최종 직업 인증이 아니다.
- `POST /admin/job-verifications/{requestId}/reject` 본문 `{"reason":"사진이 흐려 판정할 수 없습니다."}`: 거부 사유를 기록한다. 이미 처리된 요청은 다시 처리하지 않는다.
- `GET /job-verifications/me`: 로그인한 사용자의 최신 요청 상태와 거부 사유를 반환한다. 요청이 없다면 `requestId`와 `status`가 `null`이다. `appliesToCurrentJob`은 신청 직업과 현재 프로필 직업이 같은지 뜻한다. `passVerificationRequired=true`는 현재 직업의 서류 승인은 되었지만 최종 인증에 PASS가 남았음을 뜻한다.
- 승인·거부가 DB에 커밋되면 Firebase 푸시가 활성화된 환경에서 결과 알림을 보낸다. 푸시가 꺼져 있거나 기기가 등록되지 않아도 상태 조회 API로 결과를 볼 수 있다.

## 관리자 계정

- V43에서 `users.account_role`을 추가하며 모든 기존 계정은 `USER`다. 공개 API에서는 역할을 변경할 수 없다.
- 운영자가 신뢰할 수 있는 활성 계정을 확인한 후 DB에서 `UPDATE users SET account_role = 'ADMIN' WHERE id = ?;`로 지정한다. 해당 계정은 기존 로그인 API를 사용하며, 이후 요청부터 `/admin/**`에 접근할 수 있다. 관리자도 자신의 신청을 직접 심사할 수 없다.
- 관리자 사진 접근에는 S3 `GetObject` 권한이 필요하다. 버전이 있는 사진을 조회하는 경우 `GetObjectVersion` 권한도 필요하다.

## 기존 프로필·추천 응답 정리

- 본인 프로필의 기존 `jobCertificationSubmitted`는 최신 심사 요청이 현재 직업에 대한 `PENDING` 또는 `APPROVED`인 경우에만 `true`다. `jobDocumentReviewCompleted`는 최신 요청이 현재 직업에 대한 `APPROVED`일 때만 `true`다. 이전 `users.job_certification_object_key`만으로는 둘 다 `true`가 되지 않는다. 정확한 상태와 거부 사유는 `GET /job-verifications/me`를 사용한다.
- 추천 목록과 타인 상세의 기존 `jobCertificationSubmitted`는 호환성을 위해 응답 필드는 유지하지만 `false`로 내려준다. 앱은 이 값을 인증 배지로 사용하지 않는다.
- 추천 목록과 타인 상세에는 `jobDocumentReviewCompleted`를 추가했다. 해당 사용자의 최신 요청이 `APPROVED`이고 신청 직업이 현재 프로필 직업과 같을 때만 `true`다. 이 값은 서류 심사 완료를 뜻하며 PASS 기반 최종 인증이 아니다. 대기·거부 상태와 거부 사유는 타인에게 공개하지 않는다.
- `users.job_certification_object_key`는 기존 데이터 호환용으로 남아 있지만 새 화면 상태를 판정하는 기준이 아니다. React Native 앱은 업로드 후 `POST /job-verifications`를 호출해야 한다.

## 구현 시 필요한 보호 장치

- `/admin/**`는 활성 `ADMIN` 계정만 접근하도록 보호한다. 관리자 계정 지정은 운영자가 DB에서 수행한다.
- S3 사진은 공개하지 않고, 관리자만 접수된 사진을 조회할 수 있게 한다.
- 사진 원본의 보관·삭제 기간과 허용할 증빙 사진의 범위는 운영 정책으로 확정한다.
- 현재 회원 탈퇴는 사용자 행을 익명화한다. 신청 기록 및 S3 사진 정리를 탈퇴 처리에 연결했다.
- 익명화 시 새 요청과 연결된 S3 사진을 삭제한다. S3 버전 관리가 켜져 있고 업로드 URL 재사용으로 추가 버전이 생긴 경우에는 남은 비현재 버전을 정리할 수 있도록 별도 S3 수명 주기 정책이 필요하다. 제출 완료 없이 업로드만 된 사진도 수명 주기로 정리해야 한다.
